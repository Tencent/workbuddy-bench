# LLM Judge 设计说明

Host-side LLM judge（`src/workbuddy_bench/scorer/llm_judge.py`）是可选的运行后步骤，面向以测试集判分的数据集。仅在 `llm_judge.enabled: true` 且 `llm_judge.mode: host_side` 时运行；容器内 judge（Web / Office）不使用它。

它的作用很窄：有时测试失败，是因为 agent 采用了指令里没有规定的另一种约定（函数名、文件路径、输出格式等）。judge 负责修正这类情况，但不推翻客观的测试结果。

## 方案对比

我们在同一批代码题和被测模型上比较了三种设计。

| 方案 | LLM 输出 | 分数 | 结论 |
|---|---|---|---|
| 独立打分（原版） | 多个质量维度的加权分 | 加权求和 | 放弃 |
| 单测纠错型-统一版 | 所有失败测试的整体挽回率 | `tpr + 挽回率 × (1 − tpr)` | 可用，未采用 |
| 单测纠错型-独立版 | 每个失败测试一个判定 | `tpr + 挽回数 / 总数` | **采用** |

### 独立打分（原版）

这是 judge 最初的设计。模型直接给解决方案打分，不以测试结果为基准。分数更多反映方案"看起来"怎么样，而不是实际效果：测试结果相同时，轨迹长、解释详细的模型总是得分更高，模型排序因此失真。更换 judge 模型、合并或调整维度权重、增加硬性上限，都没能解决。LLM 给出的绝对分数会被过程风格污染。

### 单测纠错型-统一版

以测试通过率（tpr）为基准分，LLM 只估计失败测试中有多大比例是约定不一致、而不是真正的缺陷。这样排序恢复到与测试结果一致，每个 trial 只需调用一次。仍有两个问题：

- 缺少失败明细时，模型会根据整体上下文给出很高的挽回率，把低 tpr 的 trial 抬到远高于测试结果的分数。
- 单个整体比例无法对应到具体测试，难以复核。

### 单测纠错型-独立版（当前方案）

每个失败测试单独判定，只有能明确解释为约定不一致的测试才会被挽回。

- **最严格**：挽回率低于统一版的整体估计；不确定时默认判为真正的缺陷。
- **不会凭空挽回**：没有失败明细就没有可判定的对象，分数保持为 tpr。
- **可复核**：每个判定都附带理由。
- **排序一致**：模型排序与测试结果一致，失败更多源于接口问题的模型挽回得也更多。

代价是 LLM 调用更多（每个失败测试一次），需要控制 judge 并发。我们的实验中，对有限流的接口开高并发会导致大量判定失败。

## 当前打分规则

```
score = min(tpr + 挽回测试数 / 总测试数, 1.0)
```

- `tpr = 1.0`：直接 1.0 分，不调用 LLM。
- agent patch 为空：0 分。
- 既无失败明细也无测试计数：分数为 tpr。
- 没有 JUnit 明细但有测试计数：根据原始测试输出生成失败条目并判定。
- `tpr = 0`：挽回后最高 0.85 分。
- 只有模型明确返回 `"is_test_too_strict": true` 才算挽回；无法解析的判定不挽回。

judge 能看到的内容：指令、gold patch、agent patch、单个失败测试以及测试计数。看不到 agent 轨迹和完整的测试源码。

## 使用方式

在 job 中开启：

```yaml
llm_judge_override:
  enabled: true
  model: <judge-model-slug>   # configs/models/<slug>.yaml
```

并发由 `LLM_JUDGE_MAX_CONCURRENT` 控制（默认 4）。结果写入 `llm_judge_summary.json`，每个测试的判定在 `tasks[].per_test.verdicts` 下。
